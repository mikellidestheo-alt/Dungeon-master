## 1. The project and the rules you must keep

**Dungeon Master** is a browser Dungeon-Keeper-style game (repo `mikellidestheo-alt/Dungeon-master`, plain JavaScript, no build step, three.js vendored).
The simulation is inspired by OpenKeeper (GPL-3, a Java re-implementation of Dungeon Keeper II). You dig a dungeon with imps, claim a Portal so creatures arrive,
and defend your Dungeon Heart against waves of heroes that come through Hero Gates once a tunnel links a Gate to your Heart.

Non-negotiable:

- **Legal.** Never commit Dungeon Keeper II / EA assets (`*.sdt`, ripped media, text, level files). All art in the repo is the owner's own. Sound is fully synthesised (no audio files).
  If you copy or translate OpenKeeper *code* the project becomes GPL-3; do not. (The Pages workflow refuses to publish a `.sdt` file.)
- **Deterministic simulation.** Seeded RNG (`rand()` in `web/game.js`), fixed 20 Hz step (`step(0.05)`). Audio, UI and rendering must never call `rand()` (they use `Math.random`).
  A run must be identical with sound on or off. Any new random choice in the sim goes through `rand()`, in a fixed order.
- **Existing tests keep passing.** If a requested change legitimately breaks a test's expectation, change the test *and say why in the commit and your report*. Never delete a check to get green.
- **Always read the existing code first.** `web/game.js` is dense (one idea per line, short comments); match its style, naming and comment density.
- **The owner's style of working:** they want a short plan, then the work, then a plain-language report that says what was verified and what was not. Report failures honestly.

## 3. How to run and test (and the traps)

```sh
python3 -m http.server -d web 8123          # play: http://localhost:8123/menu.html
node tools/test_<name>.js                    # each test starts and stops its own server; PORT=<n> to choose
```

Suites (all must pass before you push): `levels objectives campaign sandbox gates chapters cursor fullscreen tabs bots audio`.
`audio` takes ~5 minutes and `bots` ~80 s; the rest are quick. Run them **one after another with different PORTs** (running many at once makes DOM timing checks flaky),
in the background, and wait with an `until grep -q DONE file; do sleep 5; done` loop. Example runner:

```sh
for n in tabs fullscreen cursor levels objectives campaign sandbox gates chapters bots audio; do echo "== $n" >> /tmp/all.out; PORT=$((8900+i++)) timeout 600 node tools/test_$n.js 2>&1 | grep -E "FAIL|passed|FAILED|Error" >> /tmp/all.out; done
```

Environment facts and traps learned the hard way:

- Playwright + headless Chromium are preinstalled (`require('playwright')` works; do not reinstall). 3D needs `--use-gl=angle --use-angle=swiftshader --enable-unsafe-swiftshader --ignore-gpu-blocklist`. Headless Chromium *does* enter real full screen.
- Tests drive the sim by hand: `window.__game` exposes the sim (`__game.G`, `step`, `build`, `tagRect`, ...), `window.__ui` the input functions. Most tests freeze `requestAnimationFrame` or set `G.speed = 0` and call `g.step(0.05)` themselves.
- **Do not use `pkill -f ...`** in a command (it matches and kills your own shell). Use `kill <pid>` or let the test's own server end.
- A screenshot cannot show the OS mouse cursor. Use screenshots (`page.screenshot`) to check layout; look at them before you claim a UI change works.
- `getComputedStyle(el).cursor`, DOM state and canvas pixels are what the cursor/UI tests check. There is no scipy; PIL and numpy exist (`tools/make_cursors.py`, `process_art.py`).
- Help text in `#help` (index.html) is a fixed 1140x152 px panel: after editing it, check `scrollHeight <= clientHeight`.
- The toolbar slot is 130 px tall; each tab panel must fit (`test_tabs.js` checks it).
- Commit messages: explain the *why*; end them with the attribution lines your own harness gives you (do not copy another session's trailer).

### 6.1 Level 1: the Knight is already waiting at the Gate

> "In level 1, the hero takes too long to appear. Perhaps have him already there waiting to be given access to by digging."

**Today.** The Tutorial (`L.tutorial` in `web/chapters.js`) has `waves: { prep: 180, plan: W('K') }`: the Knight spawns 180 s *after* the tunnel links the Gate (`heroLogic` -> `spawnWave`). That is the long wait.

**Wanted.** In the Tutorial a Knight is standing in the Hero Gate cavern from the first second. He cannot reach you (no path). The moment the player's tunnel links the Gate, he attacks immediately: no countdown.

**Design.**
- Add a general, data-driven option, not a Tutorial special case, for example `waves.waiting: true` (the wave-1 party is placed on the Gate pad when the level loads, and wave 1 "starts" when the Gate links) or a `start.heroes` list. Validate it (`validateLevel`), document it in `docs/06-levels.md`.
- A pre-placed hero is a normal `Hero` with `homeGate`. Check `Hero.update`: with no path it must simply idle (it currently does: `findPath` returns null). It must not walk through rock, and must not count as an "invasion has started" for the HUD/music.
- `G.wave`, `VAR.WAVES`, the `survive` objective (`G.wave >= VAR.WAVES && !G.heroes.length`), `G.nextWave`, the HUD countdown, `wave` objectives and `finishGame` all assume waves spawn by timer: make sure a waiting wave counts as wave 1 when it is released, and that nothing is double-counted.
- **Music/tension:** `audioMood()` derives tension from live heroes. A waiting, unreachable hero must not make the score tense for the whole tutorial; tension should start when he has a path (Gate linked) or when he is within sight. Play the wave horn (`Sound.stinger('wave')`) at the moment the Gate opens.
- Say it in the log and the guide: step 10 of the Tutorial guide ("Heroes come from the Hero Gate... one weak Knight is coming") and step 11 ("The Knight arrives soon!") are written for the old timing. Rewrite them: the Knight is *visible*, standing in the cavern; digging the tunnel is what lets him in. Objective text "Defeat the Knight" is fine.
- The tutorial must still teach: claim the Portal and get a creature *before* opening the Gate (the guide order already does; keep it, and the Knight is weak: `heroMult 0.5`).
- **Targets change.** The Tutorial used to take 5-8 minutes of which 3 were the countdown. Expect about 3-5 minutes now. Update: `tools/test_chapters.js` (section 7 expects `play.since >= 180` and 5-8 minutes), `tools/test_bots.js` (`window_[1]`), the header table in `chapters.js`, `docs/06-levels.md` (campaign table: prep 180 no longer applies to chapter 1), the Playtest checklist (Tutorial target time).
- Apply it only to the Tutorial. Other chapters keep their prep countdown. (Mention in the report that it would be easy to use elsewhere.)

**Acceptance.** Start the Tutorial: a Knight stands on the Gate pad, idle, visible in 3D (and drawn in 2D). Dig to the Gate: he attacks within a second. The scripted Tutorial playthrough in `test_chapters.js` wins. Music is calm until the Gate opens.

### 6.2 Creatures arrive only when the right buildings exist

> "Have specific monsters arrive only when certain buildings are made (example: wizards need a library)."

**Today.** `pickKind()` draws from all 14 `KINDS` by `weight` regardless of what you built.

**Wanted.** Each creature kind has a requirement (a room and a minimum size). The Portal only attracts kinds whose requirements you meet. Wizards (the Warlock, and the other casters) need a Library.

**Design.**
- Put the requirement in the data: e.g. `needs: { room: 'library', n: 3 }` on the `KINDS` entries. Count *owned tiles* of that room (there is a `roomCount`-style helper in the objectives code; reuse or share it).
- `pickKind()` must choose only among eligible kinds, still via `rand()` and still deterministic for a seed. Kinds with no requirement stay available (Goblin etc.) so the Portal never goes silent.
- Suggested table (adjust if you find a reason, and document it): **Goblin, Spider, Fly**: none (just a Lair). **Troll, Salamander, Black Knight, Bile Demon**: Hatchery (they are big eaters) or Treasury; pick one per kind and keep it explainable. **Warlock, Dark Elf**: Library (3 tiles). **Vampire, Dark Angel**: Temple (3 tiles). **Mistress**: Torture Chamber. **Assassin**: Prison. **Reaper** (rare): Prison *and* Torture Chamber. Converted prisoners and skeletons are unaffected.
- **Tell the player.** The Monsters tab (`TABS`, `renderRoster`) gets a short "Who will come" list: each kind, available or "needs a Library of 3 tiles", so the rule is discoverable. Log a line when a newly unlocked kind first arrives ("A Warlock has heard of your Library").
- **Chapter fallout.** Chapter 4 (Library) and 7 (Temple) naturally teach this; chapters 1-3 only have base kinds. Check every objective of type `creatures` with a `kind`, the Research chapter (Warlocks study best: with no Library no Warlock arrives, which is consistent), the bots (`tools/bot.js` builds rooms from objectives: it must now also build the rooms that unlock the creatures it wants) and the **sandbox** and `classic` level (apply the rule everywhere unless a level sets `rules.arrivals: 'any'`).
- Rebalance with the bots afterwards (section 8). Keep `?unlock=1` meaning "research everything", not "all creatures".

**Acceptance.** A test builds nothing but a Lair and shows only the "none" kinds arrive over many spawns; after a Library, Warlocks and Dark Elves can arrive; after a Temple, Vampires; and so on. Deterministic for a seed.

### 6.3 Lair size and Hatchery size cap the number of creatures

> "Also have a mechanic where the size of the lair limits how many monsters you can have, as well as size of hatchery as all must eat."

**Today.** The only cap is `VAR.CREATURES_SUPPORTED_BY_FIRST_PORTAL = 15`. Beds (`freeBed`: one per Lair tile) and food (Hatchery) only affect mood: extra creatures get angry and eventually leave.

**Wanted.** `capacity = min(15, beds, food)`:
- **beds** = owned Lair tiles (one creature per tile).
- **food** = a base allowance (so the first chapters work) + a number of creatures fed per Hatchery tile.
- The Portal stops spawning when `creatures >= capacity`. Nobody is thrown out if capacity later drops; the surplus is just not replaced.

**Design.**
- Constants in `VAR`: e.g. `FREE_FEED: 3` and `FEED_PER_HATCHERY_TILE: 4`. Derive the second from the sim, don't guess: a creature is hungry about every 120 s (`HUNGER_PER_SECOND 0.5`, `HUNGRY_AT 60`), a Hatchery tile lays a chicken every `CHICKEN_SECONDS` 24 s up to `MAX_CHICKENS` 12 in the world. Verify in a long headless run that creatures at capacity do **not** starve.
- **Do not break chapters 1-2**, which have no Hatchery lesson. Either rely on the free allowance (and keep their creature objectives within it or adjust them) or give levels a switch such as `rules.food: false` and use it for the Tutorial and chapter 2, with the Hatchery limit starting at chapter 3 ("Mouths to Feed"). Whichever you choose, state it.
- **Show it.** The HUD "Creatures x/15" becomes `x/capacity` with a tooltip naming the limit ("beds 9, food 12, Portal 15"). The Monsters tab summary shows the same, and a log line appears once when the Portal is waiting ("Your dungeon is full: build more Lair or Hatchery tiles"). The bonus/required objectives of the form `creatures n` need the tiles to exist: re-check each chapter's room budget (the home cavern has about 40 free tiles) and adjust objectives or add a note to the briefing where needed.
- `docs/03-game-systems.md`/`06-levels.md`/README "How a chapter goes" and the help scroll mention beds and food: update them.

**Acceptance.** A test with 4 Lair tiles and no Hatchery never exceeds 3-4 creatures; adding tiles raises the cap; the HUD shows the limiting factor; no creature starves at capacity over a 10-minute run.

### 6.4 Right click cancels the tool; the default cursor digs and carries

> "Have right click cancel the function of the cursor and resets to dig, if left click on walls, or carry creature if hovered over one and left click."

**Assumed reading.** There is a default mode (what the **Dig** button shows today). In the default mode: left-click/drag on a wall **tags it for digging**, and left-click on a **creature or imp under the cursor picks it up** (the Hand's behaviour), with no need to choose a tool. **Right-click cancels whatever tool is active** (a room, door, trap, spell, the Hand) and returns to the default mode.

**Today.** `inputDown/inputUp` (`game.js`) dispatch on the global `tool`; `'dig'` tags, `'hand'` picks up/drops, rooms/spells/doors/traps act on left click; right-drag untags in Dig and sells doors/traps when a door/trap tool is active (`removeThings`); `contextmenu` is suppressed on both canvases.

**Design decisions to make (and document):**
- Keep the tool id `'dig'` as the default (the tests and guide use it) but present it as the default mode (label e.g. "Dig / grab"); `refreshButtons` already highlights it.
- **Right-click** (press and release without dragging) with any tool other than the default: set the tool to the default, close nothing else, play a soft sound (reuse `untag` or add one), and do *not* also untag/sell. Also make `Esc` do the same if it is not closing a tab.
- **Right-drag in the default mode still untags** a box of tagged tiles (existing). **Selling a door or trap** moves to the default mode: right-click or right-drag on a door/trap tile sells it (so a player no longer needs the door/trap tool for that). Say so in the help and README.
- **Left-click on a creature in the default mode** picks it up if the cursor is within the same reach `handClick` uses (1.3 tiles) *and* the press did not turn into a drag; if it did drag, it tags as before. A press on bare wall still starts a tag box. Prefer the creature when both apply.
- **Carrying:** while a creature is carried, left-click drops it (as now). Right-click while carrying drops it at the nearest valid floor tile under the cursor (or back where it was lifted if invalid) and returns to the default mode. Keep the fist cursor logic (`syncHandCursor`, class `holding`) correct.
- Give a **hover cue**: when the default mode is active and the pointer is over a creature, show that it can be grabbed (a highlight ring under it in 3D, a thin outline in 2D). The cursor art stays the two images.
- Works in both views (the input functions are shared: `render3d.js` and `game.js` call the same `inputDown/inputUp`). Touch is out of scope.
- Update the guide/hint text where it says "choose the Hand" (the Tutorial's last step), the README controls table, the help scroll and the checklist.

**Acceptance.** A new test file (e.g. `tools/test_input.js`, modelled on `test_cursor.js` and `test_tabs.js`) covers: right-click resets Treasury / a spell / a door tool / the Hand to default; right-drag untags; left-drag on walls tags; left-click on a creature carries it and left-click drops it; right-click while carrying drops it; doors and traps sell in default mode; nothing else regresses (existing suites).

### 6.5 Creature levels 1 to 10, raised by training

> "Have a level progression and level 1 to 10 for monsters can increase through training."

**Today.** `VAR.MAX_LEVEL: 5`; XP comes only from kills (`gainXp`: `XP_PER_KILL 1`, level up at `XP_PER_LEVEL * level` = 3, 6, 9, 12 XP); each level gives hp and damage x1.18 and a 30 % heal; the sprite switches to the elite form at level 3 (`spriteOf`); research/prayer rates scale `(1 + 0.1*(level-1))`. Creatures almost never level in practice (the bots' creatures stay at level 1).

**Wanted.** Levels 1 to 10. A new **Training Room** where idle creatures train to gain XP. Kills still give a trickle.

**Design.**
- **Terrain/room:** add `T.TRAINING` (the next free id after `T.TEMPLE: 14`) with a `TERRAIN` entry (suggest `cost: 150` per tile, `own:1, room:1`), a `ROOM_TOOLS` entry, a button in the **Buildings > Rooms** group (tab layout must still fit one row: shorten labels as needed), `validateLevel` room-name support (`COND.room` uses `ROOM_TOOLS`), an objective-friendly name `training`, 2D colour in `ROOMCOL`, and 3D rendering (a floor tint plus a simple prop; **no new art assets exist for it**: draw procedurally in `render3d.js`, e.g. a post/dummy built from three.js primitives, or reuse an existing prop sprite; flag in the report that real art is wanted).
- **Behaviour:** a `'train'` state in `Creature.update`, like `research`/`pray`: an idle creature that is not hungry/tired/unpaid walks to a free training tile, trains for `TRAIN_SECONDS` (suggest 20 s), gaining XP per second, and **costs gold per session** (suggest 10-20; stop and note it if the purse is empty). One creature per tile. Respect the existing priority order (hunger before study and prayer).
- **XP curve:** replace the flat `XP_PER_LEVEL * level` with a table so that a creature that trains steadily gains about a level every 1.5-3 minutes early on and slower later, reaching 10 only in the long chapters; kills stay worth about 1 XP. Keep it data (`VAR` or a `XP_FOR_LEVEL` array). `MAX_LEVEL: 10`.
- **Stats:** x1.18 per level compounds to x4.4 at level 10: too strong. Use about x1.10-1.12 per level (about x2.4-2.8 at level 10), and make **wages rise with level** (e.g. +8 % per level) so training has a price. Check `Creature` fields that use level: research and prayer rates, `spriteOf`, the 2D level pips, the roster chip.
- **Show it:** the Monsters roster chip already shows the level; add an XP bar or tooltip ("Warlock level 4, 12/20 XP"). `gainXp` and training both play the existing `levelup` sound and log line. Add one new synthesised voice for training (a wooden strike) to `audio.js` + its `DEF` entry, and make `test_audio.js` request it (the audio test requires every voice to be reached).
- **Teach it:** the campaign needs a place for the Training Room: suggest introducing it in chapter 4 or 5, with a guide step, a short briefing sentence, and an objective or bonus objective of a new type such as `{ type: 'level', n: 5 }` ("Train a creature to level 5"; add it to `COND`, `validateLevel`, the README objective table). Do not add it as a hard requirement to chapters that already balance well; make it a bonus where unsure.
- **Bots:** `tools/bot.js` should build a Training Room in the later chapters and keep creatures training. Stronger creatures **change the balance**: see section 8.

**Acceptance.** Unit-style test in a new `tools/test_training.js` (or inside an existing suite): a creature in a Training Room gains XP and levels up to 10 and stops; wages rise; gold is spent; the level cap holds; a creature at level 10 stops training. The Training Room appears in the Buildings tab, the objective type validates, the guide step opens the tab.

## 8. Balance: re-run the bots and retune

These changes all shift difficulty (creatures arrive later or not at all, capacity limits armies, trained creatures are much stronger, the Tutorial is shorter).
`node tools/test_bots.js` plays all ten chapters on 8 seeds with two scripted players and **fails if a chapter is not winnable, is trivial, or is the wrong length** (read its header and
`docs/06-levels.md` "Balance" first). Expect to:

1. Update `tools/bot.js`: build the rooms that unlock the creatures it wants (6.2), build Lair/Hatchery to the new capacity before waiting on arrivals (6.3), build a Training Room and train (6.5). The steady bot is meant to play like a sensible newcomer; do not make it superhuman.
2. Re-measure. Then retune with **data only** (`chapters.js`: `heroMult`, `scale`, wave plans, `prep`, `interval`, gold seams, starting gold). The previous tuning targets were: steady bot wins chapters 1-8 (>= 85 %), chapter 9 about half, chapter 10 about a third to a half; the lazy bot never wins after the Tutorial and never survives chapters 6-10; bot durations inside the table of targets (Tutorial 4-8 min *before* 6.1, now shorter; 2-4: 10-12; 5-7: 12-16; 8-9: 16-22; finale 22-28; about 140 minutes in all for a fast bot).
3. If a threshold in `test_bots.js` must move because the *design* moved (for example the Tutorial's length), change it in the same commit and explain it. Stronger trained creatures will probably need higher hero strength in the late chapters; prefer that to weakening the new feature.
4. Remember the bot is a yardstick, not a person; results move by a seed or two when anything changes, so thresholds have margins.
